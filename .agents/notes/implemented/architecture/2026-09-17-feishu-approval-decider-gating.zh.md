# Agent Note: 飞书审批决策人门禁——先验证后消费的分发

Status: implemented

[English](2026-09-17-feishu-approval-decider-gating.md) | 中文

## 问题

卡片交互桥接器会结算任何携带存活交互身份的点击。`dispatch` 在检查裁决之前就删除挂起条目，畸形点击（身份合法、无裁决）因此吞掉挂起项，瀑布悬挂到请求中止为止。点击者无人校验：`operatorOpenId` 仅用于展示，聊天里任何能看到审批卡的人都能批准工具调用——群聊可见性即授予了审批权。

## 决策

- **点击先验证，验证通过才消费。** `dispatch` 先解析挂起项，对审批再要求点击携带裁决、操作者在所配决策人列表内；全部通过才删除挂起项并结算瀑布。被拒的点击回错误 toast、卡片不变，挂起项仍可被后续有效点击结算。
- **决策人是并列的 id 允许列表。** `interactionCards.approval.deciderOpenIds` 与 `deciderUserIds` 承载允许决议审批卡的 id，分别匹配回调操作者的 `open_id` 与 `user_id`，任一命中即有资格。平台是否送达 `user_id` 取决于应用被授予的权限范围——缺该字段的点击回落到 open-id 校验，门禁两种情况都 fail-closed；真实回调在特定权限范围下是否携带 `user_id` 留给真实平台验证。校验读取实时 settings 段，热生效的轮换作用于下一次点击。提问表单仍由聊天成员作答：ask-user 的答案不承载特权。
- **未配置决策人即不认领审批。** 两个允许列表均为空时桥接器不发审批卡，请求经 `next()` 透传给其他通道，与功能禁用时的透传一致。卡片可见性不确立决议权；未配置的通道不授予任何决议权。

## 被否决的备选

**认领时把决策人列表冻结进挂起项。** 为每张发出的卡快照允许列表可以穿越发送到点击之间的配置变化，但让点击校验出现两个权威；读取实时段保持单一权威，且轮换期间 fail-closed。

**未配置时 fail-open。** 允许列表为空时沿用任何人可决议的行为可以兼容既有组合，但漏洞恰好留在没人配置策略的地方；透传保持默认 fail-closed。

**每段只收一种 id 命名空间。** 用 `deciderIdType` 字段声明列表所属命名空间可以只维护一份列表，但部署方人员档案改用另一种 id 时整表要重录；两个并列列表按各自命名空间同位比较，两种条目都可直接收录。

**按派生把回合发送者设为决策人。** 自动让发起消息的发送者拥有决议权在本次被否决：群聊中发送者与审批归属人可以不同，从角色派生决策人属于持久审批缝的受信任规则解析，而非回合内卡片桥。

## 结果

审批卡从此需要至少配置一个决策人列表；启用 `interactionCards` 却两个列表都为空的部署仍保留提问卡，但其审批请求回落到其他通道——feishu-bot 示例把两个列表分别接到 `DSH_FEISHU_DECIDERS` 与 `DSH_FEISHU_DECIDER_USERS`。畸形或无资格的点击不再使挂起瀑布悬挂。该门禁覆盖的是单次回合内请求的单个卡片实例；多级链、受信任规则解析与出回合到期仍属规划中的持久审批缝，其受理点复用这一先验证后消费的形态。
